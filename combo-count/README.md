# combo-count

空中コンボの隠しパラメータ(**コンボカウント始動値 / 加算値 / 上限値**)を、ゲーム内の実測から推定するための**実験記録の置き場**。データ吸い出しは使わず、「この始動からこの列で検証技が繋がる/繋がらない」という実測の生ログと、そこから導いた下限・上限を貯めていく。

計算ライブラリではない(damage-calc とは別軸。コンボカウントは「コンボが繋がるか」を決める、move-db 寄りの技ごと隠しパラメータ)。用語は公式パッチノート表記に合わせる(始動値=Combo Count Initial Value、加算値=Combo Count Additional Value、上限値=Combo Count Upper Limit)。

## 定義

- **上限値**: `コンボカウント ≤ 上限値` ならその技はコンボできる。判定は加算前に行う(加算後モデルとは観測上区別できないので、こちらを定義として採用する)。
- **始動値**: 始動技がコンボカウントにセットする値。**始動は加算しない**(始動技はカウントを始動値にセットするだけで加算値を足さない。始動で加算するのは仕様として不自然)。
- **加算値**: 技がヒットした後にコンボカウントへ加える値。

したがって空中コンボの n 発目が判定で見るカウントは `始動値 + (n-2 発分の加算値)`。

### 喰らい方3種の意味(実測で確定)

| 喰らい方           | 意味                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| **当たらない**     | **カウント超過**                                                       |
| **追撃不可ヒット** | カウントは通過している。その技が空中やられを継続させないだけ(技の性質) |
| **追撃可ヒット**   | カウント通過 + 空中やられ継続                                          |

同じ技がカウント 0 では当たり(追撃不可)、カウント 1 では当たらなくなる例が取れており、同一技の比較なので当たり判定やリーチでは説明できない([ingrid/records.md](ingrid/records.md) の実験3・実験5)。**上限値の測定は「当たるか当たらないか」だけで判定し、追撃可否は上限値と無関係**。ODサンフレアLv3 のループが 101 発で途切れた事実はこの定義と噛み合う — 始動値 0・加算値 1・上限値 99 なら、101 発目は `C=99 ≤ 99` で通り、102 発目は `C=100 > 99` で弾かれる。

## 記録の単位系(暫定)

- **原点**: ドライブインパクト始動(壁張り付き / パニッシュカウンター)。全キャラ共通で再現できるゼロ点に置く。負の値も使う。
- **単位**: 観測された全差分の gcd を 1 とする暫定単位。刻みの細かい技が見つかったら割り直す。

## 測定プロトコル(イングリッド ODサンフレアLv3 を目盛りに使う)

ODサンフレアLv3 を連続で当てると任意のカウントを作れる。しかもこの技の後は浮きが大きく、ほぼどの技も届く距離・高さに相手がいるため、**「高さや時間が足りなくて当たらない」という交絡が消える** — 当たらなければ原因はカウント超過だと断定できる。これを目盛りに使うと3値すべてが測れる。

- **上限値**: ビームを N 回当ててカウントを `N-1` にし、検証技 X を出す。**当たる**最大のカウントが X の上限値。二分探索なら1技あたり7回程度で決まる。判定は**当たるか当たらないか**で行い、追撃可否は使わない(下記)。
- **加算値**: ビーム N 発 → X → 上限値既知のプローブ技 P。P が繋がる最大の N を求めると `N_max + Xの加算値 = Pの上限値` から加算値が出る。
- **始動値**: 空中の相手に X を当てて始動し、同じくプローブ P で測る。

限界と但し書き:

- 測れるのは**イングリッドの技だけ**。カウントは相手に乗るが、始動値/加算値/上限値は攻撃側の技の属性なので、他キャラには各自の目盛り技が要る。イングリッドが実験室になる。
- 目盛りがビーム基準なので、ビームの加算値が内部単位で 1 とは限らない。ただし下記の推論により 1 と見てよい。**反証条件**: どれかの技の上限値がビーム単位で半端な値(0.5刻みなど)になったら、ビームの加算値が 1 でない証拠なので割り直す。

### 単位の確定(実測ではなく設計意図からの推論)

ODサンフレアLv3 のループは 101 発で途切れた。始動は加算しないので、**始動後に入るビームがちょうど 100 発**、上限値は 99(カウントが 0 始まりのため)。

もしビームの加算値が内部で 2 なら内部の上限値は 199 になるが、**このループはDゲージもサンスタックも足りず実戦では成立せず、トレモの無限リソース下でしか起きない**。そのために中途半端な値を設定する動機が開発陣にない。「追撃 100 発」というキリのいい設計値の裏返しが 99 と見るのが自然で、したがって**ビームの加算値 = 1、ビーム単位 = 内部単位**とみなす。

これは実測ではなく推論であることに注意。上の反証条件に触れたら破棄する。

## 記録の形式

キャラごとにディレクトリを切り、3つのファイルに分ける(`<character>/`):

| ファイル      | 内容                                                     |
| ------------- | -------------------------------------------------------- |
| `moves.md`    | 技リスト(別名・測定対象)                                 |
| `records.md`  | **観測した事実のみ**。実験は通し番号で振る               |
| `analysis.md` | 推定・考察。根拠は実験番号で参照する。撤回した仮説も残す |

観測と考察を分けるのは、**解釈は実験が増えるたびに覆るが観測は変わらない**ため。実際に「上限値超過時の挙動」や「サンフレア=ソーラーフレア同値」の解釈は途中で覆っている。生データに解釈を混ぜると、修正のたびに事実まで書き換わる危険がある。

`records.md` の1エントリ = 1実験:

- **タイムスタンプ**: 記録日時。パッチ間比較は不可なので、日時がそのままバージョンを兼ねる
- **コンボ列**: 始動技 → 中継列 → 検証技
- **条件**: 浮きの大きさ、どの技が始動になっているか等、解釈に効く事実
- **結果**: 当たらない / 追撃可ヒット / 追撃不可ヒット(多段技なら何段目まで)
